# Architecture review

## Verdict

The core is sound and the layering is real: the workflow chain flows one direction, no engine package imports a UI view, and the profile of error handling is disciplined (%w wrapping, typed classification, few panics). The risk is concentrated at the *edges* — silent persistence loss, hand-synchronized durable state, and boundary/gate hygiene held by convention rather than enforced — plus a test process (no `-race`, self-skipping isolation lanes, thinnest coverage on the newest resume-critical engine) that would let exactly those classes of defect ship unnoticed. Nothing here is a crisis, but the consumer-visible failure mode in most of the top findings is *silent* loss or corruption, not a loud crash.

## Findings

- **critical** `internal/agent/persist.go:81`, `internal/agent/persist.go:141` — Session tails are lost with no signal: `SessionPersister` swallows DB write errors to stderr and continues (data-flow review), and `Flush()` discards `DebouncedWriter.Flush()`'s error so even the teardown flush at `lifecycle_teardown.go:61` reports nothing to the caller or exit code (error-handling review). Two reviews reached the same defect from opposite directions: every write path in session persistence is best-effort and non-reporting, so a consumer's transcript can be short and nobody — process, log, or exit code — knows.
- **critical** `cmd/yaah/tui.go:207` — The TUI redirects `os.Stderr` and stdlib `log` to `/dev/null` for the whole session (error-handling review), which is the amplifier for the finding above: every `fmt.Fprintf(os.Stderr, "warning: ...")` diagnostic (`persist.go:184/203`, the `llm/client.go` `response_format` drop) is silenced exactly when the interactive consumer is running. The only warning channel the persistence layer has is deleted by the only consumer that runs it interactively.
- **critical** `internal/workflow/exec/persist.go:218` — The settlement ledger exists twice, as live `settlementLedger` (`ledgers.go:21`) and a JSON `Ledger`, with `Checkpoint()`/`install()` hand-mapping four fields (data-flow review). Any field added to one type is silently dropped on resume — durable state loss in the feature the product is differentiated on, and the failure surfaces only after a crash-and-resume, in production.
- **critical** `internal/tools/patch.go:232` — Malformed hunk ranges are silently coerced to `start=0/count=1`, so the overlap guard at `patch.go:179` can admit a diff it should have rejected (error-handling review). This is a guard-admission defect on the path that writes to the consumer's repository: a malformed patch becomes an applied patch.
- **high** `internal/agent/lifecycle_init.go:243`, `internal/pubsub/broker.go:68` — `Publish` is lossy by construction (4096-buffer default at `broker.go:11`; a full buffer drops events, counts them as dropped, never retries), and token/thinking deltas are among its users while semantic events take `PublishMustDeliver` (data-flow review, both anchors). Under a slow view the rendered stream diverges from the persisted transcript — the consumer sees corrupted output, and the drop counter is not a user-visible surface.
- **high** `internal/pubsub/broker.go:141` — `PublishMustDeliver` spends one 50 ms budget on the whole fan-out, so the first stalled subscriber exhausts it and every later subscriber is counted dropped with no send attempt (data-flow review). `MustDeliver` is therefore not deliver-to-all: one slow consumer silently starves the rest, which is the guarantee the semantic-event path relies on.
- **high** `internal/workflow/exec/persist.go:563` — `copyNodeState`'s "snapshot" shallow-copies `[]any`/`[]*Attempt`/`[]Candidate` and `InstanceState.Bound`, so the checkpoint shares mutable references with the live reducer instead of isolating it (data-flow review). A checkpoint is not a snapshot; resume can observe post-checkpoint mutation.
- **high** `internal/mcp/rpc.go:74` — `initialize` ignores the result decode error, so a malformed handshake reply is treated as success and protocol-version mismatch detection is skipped (error-handling review). MCP integration failures present as downstream confusion rather than a rejected handshake.
- **high** `internal/agent/llm/client.go:535` — The recovery ladder branches on `strings.Contains(err.Error(), ...)` for degenerate streams, contradicting `errorclassify`'s typed-field premise; rewording those sentinels silently disables replay/fallback (error-handling review). A refactor of an error message becomes a behavioral change with no test able to see it.
- **high** `.github/workflows/ci.yml:50` — CI runs `go test -shuffle=on ./...` with no `-race`, while the agent loop, event broker, supervision drain and sub-agent runner are all goroutine-heavy (testing review). No gate anywhere checks data races on the most concurrent code in the repo — this is the process-level hole through which the broker and checkpoint findings above would ship.
- **high** `internal/tools/confinement_acceptance_test.go:62` — The headline isolation guarantee is asserted only where Landlock exists (also skips at `:66` with no Landlock), so the macOS and Windows CI legs never execute it (testing review). The product's headline claim is verified on one of three platforms.
- **high** `internal/workflow/exec/persist.go:161` — The store doc admits the reducer "re-writes the whole projection on every event", and `checkpoint()` runs from `Apply` (`run.go:274`), so write volume grows O(events²) over a long fan-out (data-flow review). This compounds with the ledger and shallow-copy findings: the newest, resume-critical engine is also the one paying quadratic writes.
- **medium** `internal/mcp/http_server.go:443` — JSON-RPC response encode errors are dropped at `443`/`446`/`211`, so a failed write is invisible to both client and logs (error-handling review). A protocol server whose responses can silently not be written is undiagnosable from either end.
- **medium** `internal/memory/debounce.go:42` — `DebouncedWriter` flushes only user-role messages immediately; assistant/tool rows linger in a pending map flushed by a timer on `context.Background()`, lost on hard exit and uncancellable (data-flow review). Same consumer outcome as the persistence cluster, different mechanism, and it is the mechanism that makes a hard exit lose the assistant side of the conversation specifically.
- **medium** `internal/agent/lifecycle_teardown.go:59` — `recover()` flattens any loop panic into `fmt.Errorf("panic: %v")` with no `debug.Stack()`, making a crash indistinguishable from a provider error (error-handling review). The one place that turns a crash into a value throws away the evidence.
- **medium** `internal/agent/loop.go:98` — `fmt.Errorf("%w: %v", ctxErr, err)` drops the provider cause from the chain, so `errors.Is` on the inner failure is impossible by design (error-handling review). Deliberate, but it means callers cannot discriminate the failure they most often need to.
- **medium** `internal/agent/pipeline/consolidate.go:102` — A background consolidation panic is only `slog`-logged; the middleware stops consolidating for the rest of the session with no user-visible signal (error-handling review). Combined with `tui.go:207`, even the log line may be gone.
- **medium** `internal/workflow/exec` — Lowest test:src ratio of the core engines (4953 test / 15119 src lines, vs dispatch 50%, agent 63%) on the newest, most resume-critical code (testing review). This is the coverage correlate of three of the critical/high findings above.
- **medium** `internal/tools/workspace_activation_live_test.go:70` — The container activation contract needs two env vars plus euid 0, so the containerd lane has zero automated coverage on any runner (testing review).
- **medium** `internal/tools/enforcement_test.go:129` — File-level `fsExempt` keys (`workspace.go`, `role.go`, `confinement.go`) skip the whole file, so a new `os.WriteFile` in those files passes the "enforcement by construction" gate silently (testing review). The strongest gate has a hole exactly in the files that matter most.
- **medium** `internal/dispatch/retained_test.go:701` — Proposal settlement/resume tests skip when the git binary is absent (also `:783`, `:818`), so the settlement differentiator is silently unverified in git-less environments (testing review).
- **medium** `internal/agent/runner/budget.go:9` — Production agent code imports `internal/tools` for `jobs.SubAgentParams`, breaking the port at `internal/agent/toolports.go:12` that exists so the loop never links built-in tools (boundaries review). One import away from the loop depending on every built-in tool.
- **medium** `internal/dispatch/aliases.go:27` — Verbatim re-export of substrate's unexported helpers (`drivePath`, `atomicWriteFile`, `keepTail`) plus `SubAgentParams` at `:23`; dispatch copies substrate internals instead of consuming a port, so substrate changes silently alter dispatch (boundaries review).
- **medium** `cmd/yaah/workflow_dag.go:419` — Mermaid DAG rendering and the node survey (718 lines here, ~6300 `workflow_*` lines in `cmd`) live in the composition root, so ACP/MCP/web consumers cannot reuse the analysis and it cannot be tested from `internal/workflow` (boundaries review).
- **low** `internal/config/validate.go:214` — The foundational config loader imports `internal/agent/budget` for `SchemaMaxIterations`: a dependency inversion from the leaf tier into the agent subtree (boundaries review). Architecturally wrong, cheap to fix, no runtime symptom.
- **low** `internal/tools/subagent_aliases.go:15` — Aliases `jobs.SubAgentParams` a second time while `delegate.go:40,218` still names `jobs.SubAgentParams`, so one package uses two names and three packages alias the same type (boundaries review). Symptom of the boundary finding above, not a separate defect class.
- **low** `internal/tools/supervisor_root_test.go:13` — Tests import `internal/agent/supervision` while production code correctly uses the `supervisionapi` seam (`supervisor.go:45`), so the neutral interface is never exercised against the concrete registry (boundaries review). The seam is asserted nowhere.
- **low** `internal/agent/supervision/service_test.go:278`, `internal/agent/agent_dispatch_test.go:355`, `internal/agent/event_delivery_test.go:65` — Timing-based tests: a 500 ms window for a negative assertion, a 250 ms sleep racing a watchdog deadline, and fixed sleeps instead of broker synchronization; 32 test files sleep and the repo has zero `t.Parallel()` calls, so the suite is fully serial (testing review, three anchors, one defect class). These are flaky-by-construction and slow rather than wrong.
- **low** `cmd/yaah/search_paths_test.go:16` — Tests assert against the real `$HOME` and a real cwd walk-up (same in `internal/agent/runner/delegate_roles_test.go:17`), so a developer's `~/.agents` layout can shape results instead of a fixture (testing review).

## Disagreements

- **Lossiness: accepted design or top risk.** The data-flow review frames the broker drops and debounced writes as "lossy by design" and locates the clearest structural hazard elsewhere (the duplicated settlement ledger); the error-handling review treats the same mechanisms — persistence errors swallowed, teardown flush error discarded, broker drops — as the highest-risk findings in its whole aspect. I ranked the silent-loss family at the top rather than averaging: "by design" describes the mechanism, not the absence of a signal, and the reviews do not actually disagree that no signal exists — they disagree on whether that is acceptable. The `tui.go:207` finding is what breaks the tie: the design's only notification channel is deleted at runtime.
- **How much structural enforcement exists.** The boundaries review concludes "every boundary observed is enforced by convention only; no test asserts the import graph", while the testing review describes "unusually strong gates — an AST scan forbidding `os.*` filesystem calls, envelope/schema parity, exhaustive event-consumer checks". Both can be true (different gates, different concerns), but they support opposite intuitions about whether architecture violations are caught mechanically, and the testing review's own `enforcement_test.go:129` finding (file-level exemptions) undercuts its "strong gates" framing for the boundary case. Do not read the testing aspect as confirming the boundaries aspect.
- No review contradicted another on a specific anchor, line, or mechanism; all three overlapping defects (session persistence, broker lossiness, workflow durability) are corroborations rather than conflicts.

## Coverage

Aspects covered: **boundaries** (import graph, type aliasing, port seams, composition-root stranding), **data-flow** (agent→SQLite, broker fan-out, workflow checkpoint/trace durability and write amplification), **error-handling** (wrapping, classification, panic recovery, protocol/parser edges), **testing** (gates, coverage ratios, platform self-skips, determinism).

Not reached by any review, though part of the architecture vocabulary this exercise implies:

- **Concurrency and lifecycle** — locking, ordering, deadlock, or shutdown sequencing were not examined as a subject; the closest is the testing review's missing `-race`. Several top findings are race-adjacent (broker fan-out, shallow-copied checkpoints) but no review audited the concurrency model itself.
- **Performance and scalability** — only the O(events²) checkpoint write appeared, and only as a data-flow observation; latency, memory envelopes, token/context growth, and fan-out scaling were not assessed.
- **Observability** — despite OTel tracing, span buffering, and a trace store being load-bearing in this repo, no review audited whether the telemetry surface covers the failure classes the other reviews found (notably the silent ones).
- **Security and isolation posture** — isolation appears only as *test coverage* of confinement (`confinement_acceptance_test.go:62`, `workspace_activation_live_test.go:70`); no review assessed the sandbox/jail design, egress rules, or the permission model on its merits.
- **API, compatibility, and schema evolution** — the settlement-ledger schema-drift finding is the symptom; no review examined the compatibility story for config, rolefile frontmatter, spec/IR versions, or the MCP/ACP surfaces.
- **Documentation and dependency management** — the doc/schema parity gates were mentioned only in passing; no review audited doc accuracy or the go.mod dependency surface.
