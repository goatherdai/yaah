Supervise the sub-agents you dispatched: one call is one tick of the supervision loop. The reply carries `done` (whether every supervised worker has finished), `ticks`, and `snapshot` — a compact view of every supervised worker (its label, feature, call and error counts, modified files, trailing tool calls, in-flight call, whether a revert is available, and how many ticks since you last intervened) — and your next call supplies `decisions` for the snapshot you just read. Workers are named by short labels (`w1`, `w2`, …) that are stable across ticks while the scope stays live; `scope` accepts either that label or a raw scope id (`scope:sub-a`).

`decisions` is a list of per-agent decisions with at most one per scope; an unlisted scope is left alone, so omit the list entirely on a tick that only observes. Each decision names its `scope`, its `action`, a `reason` (at most 20 words) and, for steer, redirect and revert, the `guidance` to deliver (at most 60 words; the successor's first message for redirect and revert). Actions are `none`, `steer`, `redirect` and `revert`, in ascending cost: **steer ≪ redirect = revert**, so match the action to the severity of what you see. `steer` is the cheapest intervention — the worker keeps its conversation and tool context and simply reads your guidance as the next message — so prefer it for drift, a missing fact (another worker is editing the same area), or a small course correction. `redirect` starts a fresh loop on the same scope with your guidance: the worker loses everything it read and tried, so use it when the agent is stuck in an obvious loop, has gone off the rails, or needs a clean re-read with new framing. `revert` is redirect plus a workspace rollback to the pre-run snapshot, discarding the files the worker edited: use it only when those files corrupt the repository or a destructive command must be undone, and note that a scope with no pre-run capture (the snapshot shows whether a revert is available) has the revert dropped rather than downgraded. Default to no decision: coding work is normal iteration, so varied tool use without errors means leave it alone. "Stuck" means 10 or more identical calls with no progress — 3 to 5 retries is iteration, not a loop. Do not intervene on a worker you acted on in the last tick or two unless it clearly ignored your guidance; a cooldown drops actions on a scope acted on within `cooldown_ticks` ticks, and drops are reported rather than silently applied.

`wait` decides how long the call blocks. `tick` (the default) applies the decisions, waits one interval with no model turns, and returns the next snapshot — one model call per tick, which is what makes your ordinary turn cycle the supervision loop. `settled` applies the decisions and then blocks until every supervised scope has finished, returning each decision's intervention record (its `outcome`, and a `drop_reason` such as `cooldown`, `not_live`, `not_reversible`, `stale`, `root_scope`, `already_claimed`, `unknown_action` or `superseded` when it took no effect), so use it when you want to wait out a batch in one call rather than one turn per tick. The reply's `ticks` counts the ticks this call ran — 1 for `wait: "tick"`, and for `settled` how many intervals the batch took to finish — and each entry in `results` carries the `tick` that recorded it, its `source` (policy or rules) and, when a claim named one, the scope registration's `generation`. `results` keeps the most RECENT per-tick records (a bounded window): a settle longer than the window drops earlier records, `ticks` still counts every tick that ran, and a note says how many were dropped. A reply with `busy` set means another `supervise` call was still in flight for this session: nothing was applied and no tick ran, so decide from the snapshot that call returned and call again on your next turn. The batch binds on the first call to the live descendants of your own scope — the session root is never a target, and the batch belongs to one calling loop, so a second loop is refused.

The dispatch pattern this tool completes: `delegate(background: true)` once per worker, then call `supervise` until `done` is true, then read the results each worker reported.

While a batch is bound, the session's advisory rule firings are delivered through that batch's queue instead of straight to the worker, and that queue is consumed only when you call `supervise`. So the rules path is only as reliable as this loop: if you stop calling the tool while supervised workers are still live — you move on to other work, finish the turn, or run out of turn budget — the routing stays armed and any firings that arrive wait in the queue (which holds at most 64, dropping the newest past that) and are never delivered. The session's teardown puts the rules engine back on direct delivery, and so does a call that returns `done`, so a run you have finished with costs one last call: call with no `decisions` until `done` is true rather than leaving the batch armed mid-session.
