Sends one subtask to a role-scoped sub-agent and returns its result. The sub-agent gets its own tool set, limits, and context; it can read, write, and execute independently.

What comes back depends on the role's output contract and the dispatch lane it selects:

- **Proposal roles** (default; e.g. developer): the work runs in an isolated dispatch world — a git worktree, or a per-dispatch container when configured — and returns `status: "proposal"` with a `proposal_id`, the changed `files`, and a `diff`. Nothing has changed on your tree — settle it with the `proposal` tool (`select`, `apply`, `release`, `discard`); an open proposal can be carried forward with `continue` or branched with `fork` instead of discarded (most often because it ran out of turns).
- **Report roles** (`output: report` in the role file; e.g. reviewer): when the role can change the workspace, its work runs in an isolated report world (worktree or container) and the result is the report itself — there is no proposal and nothing to settle. A report role with no tool that can change the workspace runs directly on the shared workspace for fresher data.
- **Shared mode** (`agents.subagent.mode: shared`): every dispatch runs directly on the workspace, and the result is its report; whatever it wrote is already applied.
- **Background** (`background: true`): returns `status` = `running`, a `job_id`, and a `label` immediately; the result arrives later as a follow-up message and can be managed with `subagent_jobs`. A plain call blocks until the dispatch returns.

Every lane — proposal, report, shared, error, and background completion — returns the **same** completion envelope. Its shared fields are `status` (`proposal`, `report`, `shared`, `running`, or `error`), `dispatch_id`, `role`, `lane` (`proposal`/`report`/`shared`), `world` (`worktree`/`container`/`shared`), `model`, `duration_ms`, `stop_reason`, and `result` (the raw report text, always present). The proposal lane adds `proposal_id`, `files`, `diff`, and `next`. A dispatch that cannot complete sets `status: "error"` with `error` (the untruncated cause), `partial` (`true` when partial output survives), `stop_reason`, and `recovery` (`retryable` plus `recommended` guidance derived from `stop_reason`).

Required: `description` (3-5 word summary — also labels the dispatch in jobs and UIs), `prompt` (the complete task), `role`. Optional: `json_mode` (structured output), `max_iterations` (1-50), `max_turns` (1-50, never below the role's `min_turns`), `output_limit` (byte cap, minimum 1024), `timeout_seconds` (wall-clock cap in seconds, 0-600; 0 or omitted uses the role's configured timeout), `provider`/`model` (per-dispatch routing override; prefer omitting — the role file or config decides; the chain is call > config role entry > role file > this session's model > config default), and `background` (boolean). `supervise` (`true`/`false`) overrides the session's supervision posture for THIS dispatch: under supervision a dispatch that WOULD run directly on the shared workspace, and whose role can change that workspace, is upgraded to the isolated report lane, so its work can be reverted by construction, and a dispatch that owns an isolated workspace and whose pre-run snapshot cannot be captured fails instead of running unrevertable. Role routing already isolates a workspace-mutating dispatch — it goes to the proposal or report lane — so today the upgrade only fires for a non-standard lane source; the promise an ordinary supervised dispatch actually gets is the second one. A read-only role keeps the shared lane — nothing it does is revertable work, and the shared lane's fresh reads are the point. A dispatch whose scope has no workspace of its own (a pure-causal fork, a container session's shared root, or a session with no retained runtime) starts with `Reversible` false: there is nothing for a revert to restore, and only `supervisor.require_reversible` turns that into a refusal. `false` keeps the lane the role's routing chose; `true` requires the session itself to be supervised; omitted follows the session. The upgrade forks a fresh worktree at HEAD, so a supervised dispatch does NOT see uncommitted edits in your working tree — commit first, or pass the content in the prompt. With `supervisor.require_reversible` on, `supervise: false` is refused and a nested dispatch (a sub-agent dispatching its own child) is refused too: neither can be made revertable. `seed_from` (a retained proposal id) seeds this dispatch's worktree from that proposal's sealed work, leaving the source proposal open; `seed_mode` is `workspace` (default) or `conversation` (same-role only). Values outside those bounds are clamped: too-large becomes the maximum, and a value below the floor means "use the role's own budget" (for `output_limit`, the minimum is used). Prefer omitting them — roles carry tuned budgets.

Use it for complex multi-step work, and for work whose raw tool calls would otherwise fill your context. Call several in one turn to run them in parallel.

Unknown argument names are rejected with the list of accepted keys, so a typo fails instead of silently changing the dispatch. `description` must be non-empty, and `prompt` is capped at 64 KiB — split a larger task and pass the relevant context.

A proposal- or background-lane report longer than the envelope's head window arrives as that head plus a marker naming the total byte count and the retrieval route: `proposal show` (with `report_offset`/`report_limit`) for a proposal, `subagent_jobs status` (with `result_offset`/`result_limit`) for a background job. The full report is retained on those lanes, so paging recovers every byte the envelope withheld; a report-lane or shared-lane result is inline with no retrieval path. `output_limit` still caps the report the runner produces and retains — paging recovers what the envelope withheld, not what that cap withheld.
